# Private backend slice

Status: implemented for local verification, disabled by default. The complete preview UI continues to use fictional, in-memory data; the separately gated `/app` routes connect the implemented durable profile and [Spaces foundation](spaces.md). This slice is not a public-launch sign-off.

## Boundary and account policy

`MARGIN_PRIVATE_BACKEND_ENABLED=1` enables the candidate HTTP handlers only after the operator has reviewed rollout gates. Clerk's server session supplies the provider subject. Headers, preview actors and submitted owner IDs never supply identity. `User.clerkId` maps that subject to an internal ID; a separate `Account` row must explicitly be `ACTIVE`. Missing, pending and deactivated accounts cannot read or write private resources. Verified personal/community invitees become ACTIVE automatically after successful profile/age setup, as defined by the authoritative [onboarding and activation rules](account-flows.md#invitation-onboarding-and-activation). Existing preview music identities remain unactivated and the original User/music columns are unchanged.

Operator activation is reserved for first-founder bootstrap and reviewed legacy PENDING recovery; normal invited members do not need it. Enabling the private-backend flag does not enable registration, activate existing accounts or change Clerk registration settings. Hosted provider configuration and session revocation still require separate rollout verification. `DELETE /api/account` deactivates Margin access; it is not full provider/account erasure.

## API contract

All responses are private/no-store and noindex. Missing configuration/provider failures deny access. Mutations require an exact configured Origin; cross-site Fetch Metadata is denied. No permissive CORS headers are emitted. Authenticated-subject Redis policies separate personal mutations (10/minute), Space/comment writes (20/minute), metadata/page reads (60/minute) and protected photo reads (120/minute). Provider failures still deny access.

| Method and path               | Input and behavior                                                                                                                                                                                                    |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET `/api/profiles/[id]`      | Active-member display name and relationship; posts/gallery only for self or accepted unblocked friends; optional opaque post-ID `before` cursor                                                                       |
| GET `/api/account`            | Own internal ID and activation state, or null; never provider identifiers                                                                                                                                             |
| DELETE `/api/account`         | Deactivate access, erase post text, revoke friendships and retire photos                                                                                                                                              |
| POST `/api/relationships`     | Strict JSON `{ targetId, action }`; request, accept incoming request, remove, block or unblock                                                                                                                        |
| POST `/api/posts`             | Strict JSON `{ body }`, 1–2,000 characters; create one friends-only text/link post                                                                                                                                    |
| POST `/api/posts/photo`       | JPEG/PNG/WebP bytes, maximum 8 MB; optional legacy `X-Photo-Description`, up to 500 characters (send percent-encoded text with `X-Photo-Description-Encoding: percent` for Unicode); create one photo post and gallery reference |
| GET/DELETE `/api/posts/[id]`  | Current audience read; owner-only deletion erases text and removes post references                                                                                                                                    |
| GET/DELETE `/api/photos/[id]` | Current audience byte delivery; owner-only deletion removes all gallery/post references and deletes the object                                                                                                        |

Clients must treat ambiguous create responses as unresolved; this first slice does not yet provide client idempotency keys or automatic retry. Successful independent create requests consume separate slots. Relationship transitions and deletion are retry-safe in their effects. Full post editing and gallery arrangement are outside this slice; owned canonical attachment reuse and bounded collection listing are implemented for Spaces; the `/app` member area offers only the implemented operations; do not connect the full preview UI until those contracts exist.

## Authorization and consistency

For personal posts/Gallery, only an active owner or an active, currently accepted friend can read the content. Space posts instead require current membership; protected photos resolve valid references for either audience. Pending requests grant nothing. A block in either direction overrides friendship; blocking removes the friendship, and unblocking does not restore it. Missing, unauthorized, deleted, expired and unreferenced resources return 404. A friend cannot edit/delete the owner's resources. Every resource request rechecks the database; no long-lived signed photo URL is issued. An already authorized in-flight response or previously saved copy cannot be recalled.

Serializable transactions lock affected user rows in a consistent order. Bounded retries cover Prisma serialization/deadlock errors, including SQLSTATE errors from raw locking queries. The account-saved IANA posting zone defines the calendar day (Los Angeles until changed); recent and prior-day usage carry forward for at least 24 hours after a zone change. Publication markers survive deletion. The allowances are: three ordinary posts or one exclusive link post, three new photographs shared across personal posts/Gallery and Spaces, and twenty personal gallery entries. Space posts have a separate write rate limit and do not use the personal post allowance; each Space retains at most twenty canonical photographs. Upload reservations count toward caps and expire after ten minutes. A photo-only addition creates a feed post and uses both allowances. Deleting a post preserves its gallery photo and both its publication and upload allowance charges. Deleting the photo removes its references everywhere, but live archived Event references reject routine photo deletion. Successful new uploads stay counted after deletion.

Foreign keys, canonical pair checks, no-self checks, bounded dimensions/body lengths and composite ownership foreign keys provide database protection. A post cannot reference another owner's photo even if DAL attachment code regresses. These constraints do not replace audience checks.

RLS is not enabled. The server DAL is the current audience enforcement boundary. With Prisma's pooled service role, RLS would require transaction-local verified identity, policies for both post and reference-derived photo audiences, separate maintenance privileges, and tests proving no connection-context leakage. That remains a useful additional defense against a missed query or SQL injection; the runtime role's lack of BYPASSRLS does not itself establish row isolation.

## Media and deletion lifecycle

Uploads are authenticated/rate limited and size bounded while reading the actual stream. The server checks signatures, rejects unsupported/animated formats, decodes with a 40-megapixel/10,000-pixel-side limit and timeout, rotates, and re-encodes WebP without EXIF/GPS/XMP. The original upload is not retained. Opaque server-generated keys and one normalized canonical asset serve both post and gallery references.

The R2 adapter sends no public ACL and produces no public/signed storage URL. Delivery checks current references and audience before reading bytes, serves a fixed image MIME/filename and forbids public caching. It never calls the public Next image optimizer. Bucket-level privacy, CDN behavior and provider credentials still require real staging verification.

Photo deletion commits denial and removes references first, then deletes the object. Success clears content metadata and the original object key and marks PURGED. Only a minimal current-day upload quota marker is retained, then a later sweep removes that row. A provider failure leaves DELETE_PENDING for retry, with reads already denied. Trusted `purgeDeletedPhotos()` and `expirePosts()` calls process bounded batches and can be rerun. Expiry denies reads synchronously even when maintenance is delayed; the expiry job hard-deletes the post row, comments, likes, notifications and attachment references; manual post deletion does the same immediately. Space deletion/expiry frees Space slots; only assets without another valid post or Gallery reference are retired. A gallery reference can intentionally retain its photo after a post expires.

The dedicated minute-by-minute worker schedules bounded, leased maintenance without a public job endpoint. [Scheduled maintenance](../src/server/jobs/README.md) covers its runtime, health checks and deployment unit. Before launch, apply the reviewed migration, install the worker and connect health alerts; verify actual object deletion, backups and restore behavior. Late writes recreate deletion intents rather than readable assets. Do not hard-delete User rows before object cleanup, because cascading deletion would discard object-key tombstones. Deactivation alone does not remove Clerk identities, backups, all identity metadata, or copies saved by recipients.

## Verification and rollout

`npm run test:social-db` creates a randomly named database on the existing loopback-only local cluster, deploys candidate migrations, grants a separate runtime role, runs actual PostgreSQL/decoder/private-filesystem tests, and drops the database. It never uses `.env` or migrates `margin_local`. The same tests are mandatory in full verification and the existing CI job, using an immutable PostgreSQL image. Clerk, Redis and R2 are mocked at the HTTP boundary; their hosted behavior is unverified. Default unit runs visibly skip the opt-in database cases; full verification runs them separately against the real database.

Before activating even a closed hosted pilot:

1. Review the additive migration on a staging clone; verify role grants, backup and rollback. Apply it with the migration owner, not the runtime credential. Existing users remain unactivated. Code rollback disables the feature; do not drop populated tables as an automatic rollback.
2. Provision approved test accounts and prove real Clerk login, cookie/origin behavior, revoked/banned sessions, recovery and activation policy. No credentials are included in source.
3. Prove the R2 bucket has no public access, authenticated byte delivery rejects other accounts and blocks, the optimizer cannot proxy it, and deleted objects/derivatives cannot be fetched through caches.
4. Prove Redis outage/limit behavior, configure appropriate read/upload resource limits, and exercise interrupted uploads, quota conflicts and ambiguous-create recovery.
5. Configure and observe retention/deletion/reconciliation workers; validate backup retention and restoration do not revive denied content. Deploy and verify the implemented [account-erasure queue, Clerk deletion webhook and independent restore journal](account-erasure.md).
6. Connect only the implemented UI paths, add end-to-end real-provider coverage, finish moderation/export/operational requirements and independently review privacy-sensitive code before public launch.

## Local setup and remaining evidence

There is no deployed staging environment. Keep cloud provisioning and deployment separate from repository work. Use `npm run test:social-db` for the isolated local journey: it covers invitation creation, automatic invited-member activation, operator-controlled bootstrap/legacy activation, persisted profile reads, posts/photos, accepted-friend access, denial/revocation and deletion. Clerk/Redis are mocked and photo bytes use a private temporary filesystem; these checks do not validate hosted sessions or bucket configuration.

For a later hosted pilot, review and deploy all additive migrations (including `20261101000000_private_profile`) with the migration role, configure the existing providers and canonical origin, then enable the backend flag after its rollout gates pass. Registration additionally needs its existing flag and invitation allowances. Follow the [current activation rules](account-flows.md#invitation-onboarding-and-activation): explicitly approve first-founder setup or reviewed legacy recovery, and verify that normal invited test accounts activate automatically after verified profile/age setup. Visit `/app` in separate account sessions; share profile links, accept friendship, refresh/sign back in, and check deletion and revocation using the actual providers. The current list returns at most 20 posts per page and 20 gallery entries; incoming requests are processed in batches of 20. No full private feed, messaging, arrangement, or account-wide export is claimed by this slice.
