## Managed authentication and account authority

Margin reuses Clerk's prebuilt sign-in, signup, email verification, MFA, recovery and account-security interfaces. Passwords and session tokens are not stored in PostgreSQL or application browser storage. Fixed application destinations are `/sign-in`, `/sign-up`, `/onboarding` and `/welcome`; successful authentication always returns through canonical database onboarding/status checks. Sign-in disables automatic signup transfer. Page-level provider failures have bounded loading, a branded retry state and an error boundary. Submitted profile and invitation fields survive failed saves.

The proxy verifies request tokens with the configured canonical origin as the authorized party. Every authenticated server action/API independently calls the shared authentication boundary: current Clerk session ID and subject must match, the session must remain active and unexpired/unabandoned, the user must not be banned/locked, and the current primary email must be verified. Upstream deletion/404 ends access. Provider/Redis failures deny access without exposing their errors; they do not pretend that logout succeeded. Verification recovery can access onboarding and Account & security before email verification, but cannot save a profile or use private APIs.

Server session checks have a ten-second ceiling and a shared Redis policy of 120 checks per verified subject per minute; onboarding allows five attempts per minute. Invitation verification uses the existing shared anonymous 20-per-minute gate without storing IP identifiers. Redis errors fail closed. Clerk still owns credential-attempt limits, bot defense, email delivery and recovery policies. These application limits do not replace provider defenses or infrastructure-level traffic controls. Current session and user reads deliberately avoid a cross-request cache to observe revocation; test Backend API capacity before a hosted pilot.

`/app` verifies authentication server-side and retains the existing domain ACTIVE-account gates. Its client monitor checks the independent, non-cacheable `/api/auth/session` endpoint on entry, visible focus/online, and each visible minute. Sign-out, session changes, deactivation, revocation and provider degradation hide private UI when observed. Cached layout content cannot restore itself after provider recovery without another server check. Server checks still protect every operation; this monitor does not erase already delivered data or undo requests already authorized before revocation. Authentication pages, private responses and the probe use private/no-store caching. The probe returns a session identifier, never a JWT or email.

Public documents preserve the root Clerk session and remain readable during account-service failures. Once Clerk reports a managed signed-in session, their header loads identity through the existing authenticated `/api/member/context` endpoint and reuses the member navigation, search, notifications and profile menu. Loading does not flash Sign in; failed member reads retain Back to Margin, while accounts requiring activation receive Account setup. Responses are scoped to the current session and discarded after a session change. Public navigation never signs out, clears cookies or redirects the document. The member logo returns to `/app/feed`. These controls are presentation; existing server authorization still governs every private request.

## Invitation, onboarding and activation

This section is the authoritative explanation of account activation. It follows [`saveOnboarding`](../src/server/account/actions.ts), [`completeAccountOnboarding` and `activateAccount`](../src/server/account/service.ts), and the [registration configuration](../src/server/account/config.ts). Other backend documents and configuration comments refer here for the current policy.

**Production registration stays closed until explicitly approved.** `MARGIN_REGISTRATION_ENABLED` is still off. The separate private-backend flag does not enable signup. Configuration requires matching instance/key modes and a canonical origin; production rejects test keys and non-HTTPS origins. Missing/invalid configuration cannot become a production preview identity.

A validated personal email invitation is stored for 30 minutes in an HTTP-only, SameSite=Lax cookie (Secure in production). This is separate from the link's 30-day validity. Only a digest is stored in PostgreSQL; recoverable share links use a server-only signing secret. Onboarding verifies the current Clerk subject and primary email and accepted provider invitation, validates profile/age fields, then atomically consumes remaining link capacity, claims the email-bound invitation and persists the canonical ACTIVE profile with three available invitation slots while releasing the sender’s slot. Expired cookies ask recipients to reopen their personal invitation email. Email mismatch recovery never discloses the invited address.

`User.clerkId` uniquely links the immutable Clerk subject to the existing PostgreSQL identity. Email and editable provider metadata cannot relink, complete onboarding or activate an account. Account owns display name, unique lowercase username, bio, onboarding/age confirmation and verification-observed timestamps. Clerk metadata is not written as a second onboarding authority. Serializable transactions, a subject advisory lock, conditional claim and bounded serialization retries cover concurrent claims/submissions. Completed setup retries return the existing result, including after registration closes or the cookie disappears; they cannot overwrite the saved profile. Deactivated accounts cannot recover access by onboarding again.

The activation rules are:

- **Personal/community invitees:** a current verified Clerk session, accepted individual provider invitation, valid email-bound Margin claim, completed profile and age confirmation produce **ACTIVE membership immediately**. Successful setup redirects to `/app`; there is no operator approval queue. New members have three available invitation slots, and completing setup frees the sender’s personal invitation slot in the same transaction. Repeated submissions neither consume another seat nor free another slot. No friendship is created automatically.
- **First-founder bootstrap:** the operator-reserved, subject-bound invitation permits setup but leaves the completed account **PENDING/MEMBER**. The guarded `account:activate` command grants ACTIVE/FOUNDER after explicit review. This bootstrap is available only while there are no ACTIVE accounts.
- **Legacy PENDING accounts:** existing completed accounts retain their saved status on setup retries or sign-in. They require deliberately reviewed operator recovery; the automatic invitation flow does not bulk-activate them.
- **Incomplete or DEACTIVATED accounts:** private resources remain unavailable. An incomplete account must finish valid setup; neither onboarding nor `account:activate` reactivates a DEACTIVATED account. A Clerk identity alone grants no Margin membership.

The operator activation command remains only for first-founder bootstrap and deliberately reviewed legacy PENDING recovery. It never reactivates a DEACTIVATED account:

```sh
# Node 22; help performs no activation.
npm run account:activate -- --help
# Only after reviewing and approving the specific account:
npm run account:activate -- --clerk-id user_ID --confirm-activation
```

The command requires the private-backend flag, Clerk secret and database, performs a read-only current identity check, and calls the same canonical transactional service tested locally. It does not send invitations, activate Clerk settings or reactivate a DEACTIVATED account. Repeating an approved activation is idempotent. The CLI uses native Node TypeScript stripping plus a narrow resolver for extensionless imports inside `src/`; this loader is never part of web requests.

After approved schema/provider configuration, an operator can issue a personal link for an existing ACTIVE member:

```sh
umask 077
mkdir -p .local
npm run --silent account:invite -- --clerk-id user_ID > .local/first-invitation.txt
```

The invitation CLI now requires `--clerk-id user_ID` for an existing ACTIVE member and writes a shareable URL through the same allowance service. Treat output as a credential, share privately, and never run issuance in logging CI. Active accounts can have three personal invitations open at a time. Acceptance with completed setup, expiry and withdrawal each free the occupied slot. The founder role is server-owned. The guarded first-founder bootstrap is only for an already verified provider identity when no ACTIVE community exists; it preserves profile/age confirmation and explicit PENDING approval. See [operator setup](#first-founder-and-operator-actions).

## Invitation membership model

Margin grows through invitations, with no public signup, referral rewards or automatic friendships. This builds on the existing `Invitation`, canonical `Account`, Clerk session checks and Redis limiter. The [activation rules](#invitation-onboarding-and-activation) define automatic invited-member admission and the limited operator recovery path.

### Membership and sharing

An ACTIVE account can have three active personal invitations at a time. Creating a link holds one slot. When a recipient accepts and completes verified Margin setup, that slot becomes available again in the same transaction. A link also frees its slot immediately when it expires or is withdrawn. Sending an email, opening the link, or starting signup does not free a slot. Sharing the same link again uses no additional slot. A failed database transaction holds no slot. The server derives available slots from unrevoked, unexpired, unused personal links, including existing links, so no scheduled reset or refund job is required. Legacy `invitationsRemaining` and `invitationAllowanceGrantedAt` columns remain for schema compatibility and no longer control issuance; no database migration is needed for this policy change.

The server-owned `Account.role = FOUNDER` permits unlimited personal invitations and community links. Browser fields and Clerk metadata cannot grant this role. Member requests containing community settings are denied; unknown fields are rejected. Founder community links accept 1–10,000 completed claims, an optional private campaign label, and a deadline within 30 days. They default to 30 days. Campaign labels and recipient emails are not public landing-page content.

Invite someone sits in Friends and the live account's Friends section. The dialog shows available slots and explicitly explains acceptance, expiry and withdrawal. Create invitation link prepares a link, then Share invitation opens the native share sheet directly from a tap; Copy link and Invite by email are alternatives. Email submission can also create a link directly; delivery failures preserve that link for retry. A native-share cancellation does not mint another link. Clipboard failures leave a selectable URL. The initially open invitation list shows link status and expiry, lets owners select an existing link to share again, and offers withdrawal. Owners can refresh after someone joins; reopening, returning to the window, and an active link's deadline also refresh availability. History is paginated. No link is automatically created just by opening the invitation dialog.

The public website provides membership information and Sign in, with no signup link. Direct `/sign-up` requires the existing protected invitation cookie to display Clerk signup. There is no code-entry form. The retired `/join` route leads to membership information. Development profile previews remain explicitly fictional.

### Recipient journey and authority

1. A member shares `https://margin.social/invite/<token>` (localhost in development).
2. GET/HEAD and messaging-app previews perform no issuance, email send, slot reservation, cookie claim or redemption. Responses are private/no-store, noindex and no-referrer; previews use generic Margin copy.
3. The recipient enters their own email. A bounded POST creates an email-bound individual `Invitation` and asks Clerk to email its own invitation. Clerk stays Invite-only. Opening Clerk's email proves inbox access and supplies its signup ticket to Margin's claim landing. Margin never handles passwords or implements a separate email-code system. See [Clerk's invitation flow](https://clerk.com/docs/guides/users/inviting).
4. The recipient explicitly continues from the personal landing. The server checks the local invitation, link status/capacity and current Clerk invitation status, then sets the existing HTTP-only, SameSite=Lax claim cookie for **30 minutes**, Secure in production. The browser carries Clerk's ticket into the existing prebuilt signup UI. A returning authenticated recipient must match the invited verified primary email.
5. Saving the profile requires a current verified Clerk session and an accepted individual Clerk invitation. One serializable transaction checks expiry, revocation, issuer status and email, increments available link capacity, claims the individual invitation and saves the canonical profile. New members become ACTIVE with three available invitation slots; the sender’s personal link becomes used and releases its slot in this same transaction. Existing completed-account retries are idempotent and never free an additional slot.
6. Successful setup redirects straight to the member app; there is no approval queue or status-check step for a valid invited member. Invitation acceptance never writes a Friendship row; friend requests still require mutual consent. First-founder bootstrap and legacy recovery retain the guarded operator path.

Personal links admit one completed claim. Community capacity counts successful Margin onboarding, rather than page views, email attempts or provider-only accounts. Abandoned requests therefore do not reserve seats indefinitely. Multiple people can receive pending emails for the same shareable link; only the permitted number can complete Margin onboarding. A Clerk identity alone never grants Margin membership. Used, withdrawn and expired links ask recipients to get a fresh invitation.

### Expiration and Clerk reconciliation

The link and Margin invitation deadline is exact: 30 days after link issuance, or the founder's earlier configured deadline. An individual email claim cannot extend it. Clerk's API accepts `expiresInDays`, with a default of 30; the installed adapter explicitly requests 30 and never ignores an existing invitation. See [Clerk createInvitation](https://clerk.com/docs/reference/backend/invitations/create-invitation).

**Clerk and PostgreSQL cannot be updated atomically.** A Clerk invitation issued after a shared link was created may otherwise outlive the link, and a provider outage can delay revocation. Margin checks its own exact deadline and revocation on every continuation and final save regardless of provider state. The emailed callback also passes through this gate. Expired or withdrawn links cannot create an eligible Margin account, even if a provider-only identity is created through a different provider entry point.

`npm run invitations:sync` expires outstanding claims and reconciles revocations using persisted markers, including depleted links and inactive issuers. It checks at most 100 pending records per invocation, sends no invitations, prints no identifiers/tokens/emails, and exits nonzero on provider failure. Withdrawal and completed onboarding also attempt it immediately. Failed or ambiguous deliveries without a known provider ID remain retryable instead of being falsely marked complete.

Before real invitations are enabled, deploy the implemented `maintenance:work` worker, which schedules reconciliation every minute alongside content cleanup. Its database leases prevent duplicate worker execution and its health command reports failures, staleness and possible backlog. The manual sync command remains available. See [scheduled maintenance](../src/server/jobs/README.md) for the service unit, migration and monitoring setup. There is no public job endpoint. Its availability and provider-only revocation latency are launch dependencies, not a claim of instantaneous cross-provider consistency. Do not enable real invitations until this limitation and its operational monitoring have been verified.
